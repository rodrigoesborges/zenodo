# AGENTS.md

Nextcloud server app (`zenodo`) that lets users publish files from Nextcloud to
[Zenodo.org](https://zenodo.org) as draft depositions. It is **not** a standalone
PHP project: it runs inside a Nextcloud server (33–36), loaded by Nextcloud's
app framework. There is no composer.json (only `OCP` interfaces are used) and no
test suite; the frontend is built with Vite.

## Commands

- `npm install` — install frontend dependencies.
- `npm run build` — production build into `js/` (builds are **committed**).
- `npm run dev` — rebuild on file change.
- `make appstore` / `make release` — packaging (excludes `/node_modules`, `/src`,
  `/vendor`, `/package.json`, `/package-lock.json`, `/vite.config.mjs`).

Version is duplicated: `version+=2.0.0` in the `Makefile` and `<version>` in
`appinfo/info.xml`. Keep both in sync. PHP lint:
`find lib appinfo -name '*.php' -exec php -l {} \;` (CI does this; locally use
docker `nextcloud:32-apache` if no PHP is installed).

To run/test, copy or symlink the repo into a Nextcloud `apps/` directory, run
`npm run build`, and enable it; validation is manual through the Files UI and
the admin settings page.

## Coding style

Tabs, PSR-2-ish (class brace on end of line, no space after type cast),
camelCase, one class per file. PHP 8 features in use: constructor property
promotion, promoted services, `match`, nullsafe operator, attributes
(`#[NoAdminRequired]`) — **not** docblock annotations. Every PHP file starts
with the AGPL header block. Frontend is ES modules, no jQuery, no Vue.

## Layout and architecture

### Backend (AppFramework, autowired)

- `appinfo/info.xml` — metadata, `<nextcloud min-version="33" max-version="36"/>`,
  admin settings section registration (`OCA\Zenodo\Settings\Admin`).
- `appinfo/routes.php` — REST routes. Route names use `controller#method`
  (`settings#...`, `Zenodo#...`). The JS must stay in sync with these URLs.
- `lib/AppInfo/Application.php` — `App implements IBootstrap`. **No manual
  container registration**: controllers and services are autowired (the
  `string $appName` constructor parameter is injected automatically; services
  use `Application::APP_ID` instead of receiving the app id). Registers the
  `LoadAdditionalScriptsEvent` listener which injects `zenodo-main` + `navigate`
  CSS into the Files app.
- `lib/Controller/SettingsController.php` — admin-only token endpoints (no
  `NoAdminRequired`).
- `lib/Controller/ZenodoController.php` — dialogs (`TemplateResponse` render
  mode `'blank'`, template chosen by `$type`), deposit state, creator lookup,
  publish/upload flows.
- `lib/Service/ApiService.php` — Zenodo (InvenioRDM) REST client via cURL
  (Bearer auth). Create draft `POST /records`, upload via the 3-step
  init/PUT-content/commit files flow, list drafts `GET /user/records`.
- `lib/Service/FileService.php` — resolves file ids to nodes for the current
  user and produces a local path (temp copy for non-local storages).
- `lib/Service/ConfigService.php` — app config values (`tokenSandbox`,
  `tokenProduction`).
- `lib/Db/` — `DepositionFiles` entity (`addType` integer casts) +
  `DepositionFilesMapper` (QBMapper, query builder).
- `lib/Migration/Version2000000Date20261004000000.php` — creates
  `zenodo_depositions_files` (guarded with `hasTable` for installs coming from
  the old `database.xml`). Discovered automatically, no registration needed.
- `lib/Settings/Admin.php`, `lib/Listener/LoadAdditionalScriptsListener.php`.

### Frontend (Vite, vanilla JS)

- `src/main.js` — entry for the Files app. Uses
  `registerFileAction({...})` from **`@nextcloud/files` v4 with plain action
  objects** (the `FileAction` class does not exist in v4; older lib versions are
  silently ignored by the Files app). Two actions: new deposition and add file.
- `src/dialog.js` — fetches the server-rendered dialog HTML
  (`GET /apps/zenodo/dialog/{type}`) and shows it in a custom modal overlay
  (`.zenodo-modal-overlay`, `#zenodo-dialog`; no jQuery UI). Drives the creators
  list with DOM APIs (`textContent`, never `innerHTML` for user data).
- `src/admin.js` — entry for the admin settings page (token form).
- `vite.config.mjs` — two entries `zenodo-main` / `zenodo-admin` into `js/`;
  `emptyOutDir` is **on**, so `js/` is fully regenerated by each build (shared
  chunks like `translation-*.js` are normal — commit them).
- `templates/` — `dialog.newdeposition.php`, `dialog.addfile.php` (fragments
  loaded via axios; element ids are `zendialog_*` and are referenced by
  `src/dialog.js`), `settings.admin.php`.

## Data flow / conventions

- JSON responses are plain PHP arrays; success shape is
  `{success: true, ...}`, errors are `{success: false, error: string}` — no HTTP
  status codes for API errors.
- `$production` arrives from JS as `true` **or** the string `'true'`; normalize
  with `($production === true || $production === 'true')` before use.
- `node.id` from `@nextcloud/files` v4 is a **string**; controllers cast with
  `(int)`.
- The Zenodo `access` schema has **no "conditions" field**: open =
  `{record:'public',files:'public'}`, embargoed = restricted files + embargo
  date, restricted/closed = `{record:'restricted',files:'restricted'}`. Mapping
  lives in `ApiService::mapAccess`.
- Resource type ids are `publication-*`, `image-*`, `poster`, `presentation`,
  `dataset`, `software`, `video`, `lesson`, `other`; license ids are lowercase
  (`cc-by-4.0`, `mit`, `apache-2.0`, ...) via `metadata.rights: [{id}]`.
- Legacy deposit API (`/api/deposit/depositions`) is deprecated — do not use.
- Republishing a file already sent to production is blocked in the frontend
  (`depositId !== 0 && type === 'prod'` check against `GET /deposit`).
- `DepositionFilesMapper::deleteFile($fileId, false)` deletes only `sandbox`
  rows, preserving the production history; `storeDepositionFile` calls it
  before inserting.
- ORCID integration is a soft dependency of the `orcid` app (guarded with
  `App::isEnabled` + try/catch `\Throwable`).
- CSRF is enforced everywhere (no `NoCSRFRequired`); `@nextcloud/axios` injects
  the request token.
- `l10n/` is generated from Transifex (`.tx/config`). **Do not edit by hand**.

## Gotchas

- `js/` must be rebuilt (`npm run build`) after any change in `src/` — the
  committed bundles are what runs.
- The `zendialog_publicationtype` / `zendialog_imagetype` selects and the
  embargo date row are shown/hidden by JS based on the parent selects.
- Creator names must be `Family, Given` (a comma is required) because the API
  payload maps `family_name`/`given_name`; comma-less names become
  organizational creators.
- Tokens are app-level (global), not per-user.
